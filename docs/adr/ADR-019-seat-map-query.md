## 문제

좌석 맵은 조회 시점의 스냅숏이다. 사용자가 맵을 보고 좌석을 고르는 사이 다른 사용자가 그 좌석을 선점하면, 맵에서는 빈자리였던 좌석의 선점이 "이미 팔림"으로 실패한다. 이 문서는 이런 실패를 헛선점이라고 부른다.

지금 좌석 맵 API(`GET /api/schedules/{id}/seats`)는 캐시 없이 요청마다 회차 1만 석을 SQL 한 문장으로 읽는다. ADR-014는 이 API를 초당 최대 20번으로만 쟀다. 20만 명이 맵을 반복해서 새로 고치면 DB 부하가 커지고, 캐시를 두면 맵이 실제보다 더 늦어진다.

## 가설

불일치 자체는 없앨 수 없다. 캐시가 없어도 사용자가 맵을 보고 고르는 시간만큼 맵은 늦다. 조회 방식이 정할 수 있는 것은 두 가지다. 하나는 맵이 실제 상태보다 얼마나 늦은가(화면 나이)이고, 다른 하나는 그 대가로 DB와 선점 경로가 얼마나 부담을 지는가다.

## 설계

### 설계-1. 응답은 고를 수 있는지만 알린다

좌석 맵 응답의 좌석마다 `status`(AVAILABLE, HELD, RESERVED) 대신 `available`(true 또는 false)을 낸다. 화면이 묻는 질문은 "이 좌석을 지금 고를 수 있나" 하나이고, 화면은 HELD와 RESERVED를 어차피 같은 모양으로 그린다(2026-11-22 사용자 결정). 서버 안의 좌석 상태(`SeatStatus`)와 선점, 확정 경로는 그대로다. 만료 방식마다 홀드를 어떻게 보이게 하는지도 ADR-014의 판정을 그대로 쓴다.

이 결정에는 캐시 쪽 효과도 따라온다. 정상 확정(HELD → RESERVED)은 `available`을 바꾸지 않는다. 그래도 갱신은 방향을 가려서 하지 않는다. 결제 뒤 대체 배정은 빈 좌석을 바로 RESERVED로 만들고(AVAILABLE → RESERVED), 조건 없는 확정은 만료로 풀린 좌석을 RESERVED로 만들 수 있기 때문이다. 그래서 좌석 상태를 쓰는 경로는 방향과 상관없이 모두 그 회차의 맵을 갱신한다.

### 설계-2. 비교할 조회 방식

측정(2단계)에서 비교할 방식은 다섯 가지다. 앞의 네 가지는 같은 API 뒤에서 설정 옵션 `seat.seat-map.mode`로 고르고, 푸시는 따로 켜는 엔드포인트다. 기본은 캐시 없음이고, 측정 뒤에 정한다.

| 이름 | 설정 | 방식 | 화면 나이의 상한 |
|---|---|---|---|
| 캐시 없음(베이스라인) | `none` | 요청마다 SQL 한 문장 | 조회 시간 |
| 앱 안 TTL 캐시 | `ttl` | 앱 메모리에 회차별 맵을 TTL 동안 둔다 | TTL |
| Redis 공유 캐시 | `redis` | 앱 여러 대가 Redis에 둔 맵 하나를 같이 본다 | TTL |
| 변경 시 갱신 | `event` | 맵을 바꾸는 쓰기가 커밋된 뒤 그 회차 캐시를 지운다 | 커밋에서 무효화까지 |
| 상태 푸시(SSE) | 엔드포인트 켜기 | 연결 직후 전체 맵, 그 뒤 바뀐 좌석만 보낸다 | 커밋에서 전송까지 |

### 설계-3. 변경 시 갱신이 지켜야 하는 것

변경 시 갱신과 푸시는 맵을 바꾸는 쓰기를 하나라도 빠뜨리면 조용히 낡은 맵을 계속 보여 준다. 그래서 1단계 구현은 좌석 상태를 바꾸는 쓰기 경로를 전수 찾아 무효화 지점과 짝지은 점검표로 남기고, 경로마다 "쓰기 뒤 다음 조회에 반영된다"를 테스트로 확인한다. 대상은 1석 선점, 묶음 선점, 해제, 만료 배치, lazy 만료 방식의 회수, 대체 배정이다. 무효화는 커밋 뒤에만 한다. 롤백된 쓰기가 맵을 바꾸면 안 되기 때문이다.

무효화만으로는 부족한 순서가 두 가지 있다. 첫째, 캐시가 빈 상태에서 조회 A가 DB를 읽은 뒤 캐시에 넣기 전에 다른 쓰기가 커밋하고 무효화하면, A는 무효화보다 늦게 옛 맵을 캐시에 넣는다. 그 뒤로는 다음 쓰기가 올 때까지 옛 맵이 나간다. 그래서 회차마다 세대 번호를 두고, 무효화는 세대를 올리며, 조회는 DB를 읽기 전의 세대가 그대로일 때만 캐시에 넣는다. 둘째, loadtest 초기화는 회차를 지우고 같은 id로 다시 만든다. 회차 하나를 무효화하는 것으로는 지워진 회차의 캐시가 남으므로, 초기화는 커밋 뒤 캐시 전체를 비운다.

푸시는 연결 직후의 첫 맵과 그 뒤의 변경 사이에 빈틈이 생기면 안 된다. 첫 맵을 읽은 뒤에 구독을 걸면 그 사이의 변경을 영영 놓친다. 그래서 구독을 먼저 걸어 변경을 쌓아 두고, 첫 맵을 읽어 보낸 뒤, 쌓인 변경을 보낸다. 변경 신호에는 좌석 id만 싣고, 보낼 때 그 좌석의 지금 보이는 상태를 다시 읽는다. 같은 좌석의 변경이 첫 맵과 겹치거나 순서가 바뀌어 도착해도, 클라이언트가 마지막으로 받는 값은 지금 상태다.

lazy, lazy-sweep, derived 만료 방식에서는 쓰기 없이 시각만 지나도 홀드가 풀린다. 이 만료는 이벤트로 잡을 수 없으므로, 변경 시 갱신과 푸시는 sweep 만료 방식에서만 쓸 수 있다. 다른 만료 방식과 함께 설정하면 앱이 기동을 거부하고, 거부 메시지에 되돌릴 설정을 적는다.

### 설계-4. 캐시의 한계

앱 안 TTL 캐시와 변경 시 갱신의 캐시는 앱 프로세스 안에만 있다. 앱이 여러 대면 대마다 맵이 다르고, 다른 대에서 일어난 쓰기는 무효화하지 못한다. 여러 대가 같은 맵을 보는 것은 Redis 공유 캐시의 몫이고, 여러 대 사이의 무효화는 이번 범위 밖이다. 푸시도 같다. 연결된 앱에서 일어난 변경만 보낸다. Redis 공유 캐시는 Redis를 읽거나 쓰다 실패하면 DB 조회로 응답하고 실패 수를 지표로 남긴다. Redis 장애가 맵 조회 장애로 번지지 않게 하기 위해서다. Redis 공유 캐시는 TTL로만 낡음을 막고 쓰기 경로의 무효화를 받지 않는다. 캐시에 넣는 맵의 나이는 DB를 읽기 시작한 시각부터 센다.

## 측정 계획 (2단계)

측정은 2단계 명세에서 정한다. 이 절은 1단계 구현이 값을 낼 수 있어야 하는 지표만 적는다(2026-11-22 사용자 결정).

| 지표 | 뜻 |
|---|---|
| 헛선점 비율 | 맵에서 빈자리로 보고 고른 좌석의 선점이 "이미 팔림"으로 실패한 비율 |
| 화면 나이 | 응답한 맵이 실제 상태보다 늦은 시간(p50, p99) |
| 조회 처리량과 p99 | 좌석 맵 조회의 처리량과 테일 레이턴시 |
| DB CPU와 선점 p99 | 조회 부하가 DB와 같은 시간의 선점 API에 준 영향 |

부하는 두 가지로 건다. 방식마다 조회를 올려 가며 한계 처리량을 찾고, 모든 방식이 버티는 같은 고정 부하에서 위 지표를 비교한다. 20만 명이 5초마다 새로 고치면 초당 4만 번이라(직접 계산: 200,000 ÷ 5) 실험 장비로는 그대로 만들 수 없다. 푸시는 연결 수천 개 규모로 재고, 20만 연결로 늘린 값은 추정이라고 적는다.
